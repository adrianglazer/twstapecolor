# Level 2 isolation, size contrast and resource review — v0.3.16

Verified on 2026-10-15 against a freshly restarted TWS 10.51.1c. The user confirmed native Level 2 colors were restored by restarting; v0.3.15 was not enabled in that fresh session. All **6,368 automated checks** pass under `-Xverify:all`.

## Persistent Level 2 color loss: cause and fix

The native `jtable.basic.TextRenderer` extends `DefaultTableCellRenderer`. Its `isOpaque()` answer depends on its current parent and background: it can return false while its underlying opaque flag is true. The old painter saved that computed answer and restored it using `setOpaque(false)`, permanently changing the shared renderer. Level 2 still had a colored background value but no longer painted it. Restoring the original table bytecode did not repair this state. Earlier restoration checks used the computed getter and did not catch this latent change.

A separate headless reproduction using the actual JDK renderer demonstrates the failure: after painting in a matching black table, changing the renderer background to the Level 2 color leaves `isOpaque=false` with v0.3.15; v0.3.16 correctly retains `isOpaque=true` in that later context. A regression test covers this exact transition.

v0.3.16 applies background fills through a private graphics wrapper. It never writes shared native background/opacity properties and never reparents the renderer. Text, icons, clipping and transforms pass through to the native graphics. Only temporary renderer bounds are restored after painting. Each cached wrapper rechecks its exact owning tape table before data access or row translation; non-tape use bypasses all tape behavior. Start/probe repaints are restricted to tape tables.

## Colors and size contrast

Defaults are ask green `#16834A` and bid red `#B83B4B`. Intensity is `0.18 + 0.82 * sqrt(size / largest visible size)`. For a 10,000-share maximum, 100 / 1,000 / 10,000 shares use 26.2% / 43.9% / 100% intensity. Tests check monotonic shading, visible RGB separation, native white text pixels and colored icon shapes. Quote classification and the 50-trade limit are unchanged.

## Live isolation, accuracy and restoration

- **60 paired Level 2 renders** across two depth tables: each native render was followed by repeated tape paints and another depth render within the same EDT turn. All pairs were pixel-identical, with zero tape wrappers, sorter changes or errors. Colored depth rows remained present. Actual screen captures were visually reviewed.
- **40 incoming trades** (3 ask, 19 bid, 18 neutral), **40 quote-size snapshots**, **1,914 colored cell checks**: zero quote/trade, arrival-book, direction, RGB or paint-restoration mismatches and zero errors.
- **Three stop/start cycles:** all 42 stable table properties and normalized target method fingerprints matched the fresh native baseline after each stop; no tool calls remained in the three target methods.
- **20 further paired Level 2 renders** around the final stop/restart verification: zero pixel differences, wrappers, sorter changes or errors; native depth colors stayed visible.
- The [enabled capture](docs/screenshots/colored-v0.3.16.png) and [native capture](docs/screenshots/native-v0.3.16.png) show both depth tables alongside the enabled tape, and the native appearance after stop. They are unaltered screen crops from different live moments.

The newly built production class bytes were compared with the JAR used in the live run: every class matched exactly. Coloring was left enabled after verification.

## Resource behavior

Per-view native renderer wrappers and tint components are reused, with at most 64 delegate entries per view. Closing a displayed table removes its view, listeners and renderer cache; pending installations are canceled if a displayed table closes first. Tests include 100 rapid close-before-install cycles. Trade and market-record caches remain capped at 4,096 and 64; the corresponding current-trade map is also bounded. Tests push 100,000 trade events under a **64 MiB** heap limit.

Native field reflection is cached per class. Unrelated quote notifications are rejected using an immutable identity lookup before acquiring the feed callback lock. Normal operation starts no polling worker and persists no debug logs.

A separate JVM benchmark rendered 100,000 cells: v0.3.15 allocated **273,722,384 bytes** versus **186,722,520 bytes** for v0.3.16 (about **32% less allocation**). Wrapper and paint-component identity changes fell from 100,000 each to one each. Sampled EDT CPU time fell from 1,738 ms to 1,192 ms in these synthetic runs; this is not an end-to-end TWS speed guarantee. A further **1,000,000 paints completed with `-Xmx64m`**, reusing one wrapper/component; it allocated 1.78 GB cumulatively through GC without exhausting the 64 MiB heap.

A 1 Hz sampler and bounded JFR profiles compared native TWS with five minutes of ordinary enabled operation, after correctness audits ended. No live GC was forced.

| Measurement | Native, 45 samples | Enabled, 300 samples |
| --- | ---: | ---: |
| Average whole-process CPU, cores | 1.31 | 1.06 |
| Heap used range, MiB | 238–449 | 234–455 |
| EDT queue delay, 95th percentile | 0.14 ms | 0.15 ms |
| Maximum sampled EDT delay | 1.04 ms | 1.06 ms |
| GC time / measured elapsed time | 268 ms / 44 s | 891 ms / 299 s |

Enabled per-minute heap minima were **236.1, 237.6, 240.7, 233.6 and 242.9 MiB**, with ordinary GC fluctuations rather than sustained monotonic growth during the sample. Final tool caches held **2 views, 616 trades, 1 quote record and 1 current trade**. Most sampled CPU activity was in native `jextend.cE.f` both with coloring off (3,277/4,072 execution samples) and on (21,992/26,569); 20 enabled execution samples contained a tool frame. This is evidence that substantial CPU usage existed without the script. Sequential live intervals have different market activity and cannot establish causal CPU savings or rule out every long-duration problem.

One million synthetic paints, bounded caches and a five-minute live sample provide practical resource checks; they do not prove behavior over days or across all TWS versions. Opt-in diagnostic agents release their retained table/event collections when they finish. All raw profiles, CSVs and captures remain under Git-ignored `work/logs/`; normal logs remain opt-in. Reproduction tools are documented in [tests/live](tests/live/README.md).

# Live-update flicker fix — v0.3.15

Tested on 2026-10-15 in the same running TWS 10.51.1c session. All **6,334 automated checks** pass under `-Xverify:all`, including 208 new immediate-paint checks.

The v0.3.14 model listener cleared the classification map before queuing its rebuild. A paint between those steps received a neutral result. The new version marks the map dirty and refreshes current model classifications on demand before painting; it never reuses stale row-index classifications. Sorter/filter changes stay deferred, and identical included-row sets no longer reset the filter. Frozen quotes, color rules and size-adaptive intensity are unchanged.

A temporary model listener sampled the exact event/rebuild gap in live TWS:

| Version | Duration | Model events / gap samples | Directional row checks | Transient neutral results | Wrong sides | Errors |
| --- | ---: | --- | ---: | ---: | ---: | ---: |
| v0.3.14 | 20 s | 3 / 3 | 33 | 33 | 0 | 0 |
| v0.3.15 | 30 s | 5 / 5 | 18 | 0 | 0 | 0 |

The first three gap renders were saved locally and visually reviewed. The fixed renders retain green backgrounds while the filter refresh is pending. Rows predating the fresh attachment remain neutral as designed.

A separate 30-second accuracy audit checked **13 incoming trades** (3 ask-side, 2 bid-side, 8 neutral), **13 quote-size snapshots** and **918 colored cell paints**, with zero quote/trade, direction, RGB or component-restoration mismatches and zero errors. All 13 fresh arrival-book comparisons matched. Actual on-screen tape crops were also reviewed. Unlike the older audit, the revised audit does not skip observations just because filter work is pending; this particular pixel run encountered zero pending observations, so the dedicated gap audit supplies that coverage.

Stopping v0.3.15 restored all **42 compared properties and method fingerprints**, with zero mismatches and zero remaining tool calls in the three target methods. Coloring was restarted after verification. Evidence is under ignored `work/logs/flicker-*`; reproducible tools are in [tests/live](tests/live/README.md).

The earlier audit below skipped one pending observation, so it did not establish update-gap stability. These bounded samples establish the observed flicker fix, not a guarantee against all possible display issues. Shading can still change when a larger trade changes the adaptive scale.

## Does stop restore the previous state?

**Yes for the checked stable table state and instrumented methods in v0.3.14.** Three live start/status/stop cycles each compared 42 properties against a clean native baseline, with zero mismatches. These include the original table/model identities, null sorter, row height, selection settings, column order/widths, foreground/background and underlying model/property-listener identities.

All three target methods had identical normalized instruction fingerprints before start and after stop, with **zero `twstapecolor` call instructions**. Constant-pool layout and debug metadata are excluded from the fingerprint. Live prices and row counts are excluded from table-state equality because market data continues updating. Loaded helper classes remain in the JVM until restart; stop restores execution behavior rather than unloading classes.

Stopped-state screenshots show native backgrounds; multiple enabled-state screen captures show red, green and neutral rows across all three columns. Offscreen renders and actual screen crops are saved locally for comparison.

## Issues found and fixed

1. **Wrong transformer owner after another attach command.** Older versions replaced the registering instrumentation handle on every command, so removal could fail silently. The owner is now retained and removal failure is explicit. The regression uses different instrumentation instances for start, status and stop.
2. **Selection cleared by sorter changes.** Selection is now translated through model rows when installing and removing the private filter; column selection and lead/anchor state are preserved.
3. **Missing top record retained stale quote data.** Missing/unreadable top data invalidates the cached quote, leaving subsequent trades neutral until a usable quote is observed.
4. **Current-trade cache exceeded the record bound.** New records beyond the 64-record limit are no longer added to that cache.
5. **Callback raced with stop.** Quote/trade callbacks and stop are serialized; stop waits for a running callback before clearing state. A blocked-callback regression verifies that caches cannot reappear afterward.
6. **Partial start left a renderer transformer.** A failed feed-hook setup now rolls back a newly installed renderer hook.

The deeper audit found five inactive legacy renderer-call instructions in the existing JVM despite the old stop message. A one-off, explicitly scoped cleanup made the three disabled legacy transformer bodies inert and retransformed the native selector. This recovery is not part of normal startup. v0.3.14's repeated cycles restored native instructions without additional cleanup.

## What this proves

These measurements establish consistency with the TWS book, locally observed quote/trade delivery, classification rule and painted output during the samples. They do not independently establish the market-data provider's NBBO correctness, exchange-level ordering, latency or aggressor identity. The independent oracle normalizes binary noise to 12 significant digits for the stock prices sampled; it is not a universal precision policy for every instrument. Historical trades with no captured preceding quote remain neutral.
